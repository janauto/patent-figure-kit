# 验收套件

这份套件用来回答一个问题：**这台机器上，这套工具是不是每个功能节点都真的能用？**

分两层，缺一不可：

| | 测什么 | 谁来判 | 文件 |
| --- | --- | --- | --- |
| 第一层 | **工具链**功能完备性 | 脚本，客观判定 | `run_acceptance.py` |
| 第二层 | **模型**是否守规矩 | 人看对话记录 | [行为验收.md](行为验收.md) |

第二层不能省。v1 那次事故里，工具链的每个零件单独看都能跑，
出问题的是模型在能力不足时自己写了 170 行临时脚本——**这类问题脚本测不出来**。

---

## 第一层：跑一条命令

```bash
python3 acceptance/run_acceptance.py
```

约 40 秒，输出一张 14 行的结果表。退出码 `0` = 全通过，`1` = 有节点未通过。

需要机器可读结果时加 `--json`：

```bash
python3 acceptance/run_acceptance.py --json acceptance-report.json
```

### 它检查的 14 个节点

| 节点 | 内容 | 判据 |
| --- | --- | --- |
| N1 | 环境自检 | 必需依赖全部就位 |
| N2 | 装配体解析 | 8 种零件 / 11 实例 / 主轴判为 z，输出过 schema |
| N3 | 计划校验 · 正例 | 合法计划退出码 0 |
| N4 | 计划校验 · 反例 | 三类典型错误各自命中预期错误码，**且都带修复提示** |
| N5 | 出图 | 渲染出 2 张图 |
| N6 | 附图标记 | 号码连续不重复、说明文本与标记表逐条对得上 |
| N7 | 质量闸门 | 每张图 13 项全过 |
| N8 | **闸门有效性** | 把合格图的引线锚点搬离 40mm，闸门必须判 FAIL |
| N9 | 确定性 | 同一计划渲两次，规范化哈希逐位相同 |
| N10 | **跨机器一致性** | 与仓库记录的金样哈希逐位相同 |
| N11 | 合规 | 图上无明细表、无厂内件号、线型全连续 |
| N12 | BOM 导入 | 件号→中文名匹配可用 |
| N13 | DWG 转换 | AutoCAD 或 LibreDWG 任一可用即可（都没有则跳过） |
| N14 | 单元测试 | pytest 全绿 |

两个节点值得单独说：

**N8 是闸门的自证。** 一套永远说 PASS 的闸门等于没有闸门。
这一条故意把一张合格图弄坏，闸门若还放行，说明它是摆设——
这时候 N7 的「全项通过」也就不可信了。

**N10 是整套架构的核心命题——但要把它证明的范围说准。**
仓库里存着两个哈希，是在一台特定机器上渲出来的。你这台机器渲出同样的哈希，
证明的是：**全新克隆、另一个运行时、另一个进程，产出逐位相同。**

它**不**自动证明「跨机器」。如果你跑在录制金样的同一台机器上，
环境本来就一样，跨机器这一维并没有被检验到。要真正验证，
需要在**不同操作系统或不同 OCCT 构建**的机器上再跑一次，把哈希对回来——
那才是「换机器也一样」的硬证据。

> N10 失败不一定是缺陷。最常见的原因是依赖版本与 `requirements-pinned.txt` 不符——
> 脚本失败时会把本机版本一并打出来。核对版本后仍不一致，请把两边哈希都反馈回来。

### 跳过与失败的区别

- **跳过**：这台机器不具备条件（例如没装 AutoCAD 也没装 LibreDWG），不算失败。
- **未通过**：功能确实不完备。每条都带具体原因，请**原样反馈**，
  不要只说「跑失败了」——detail 里已经写清了是什么问题。

## 第二层：五道行为题

见 [行为验收.md](行为验收.md)。按顺序问完，留完整对话记录。

五道题分别测：能不能说清自己的边界、会不会自己写脚本、
号码是不是自己编的、撞了闸门会不会改脚本绕过去、越界请求挡不挡得住。

**判不通过不是坏事。** 任何一处不通过都指向 SKILL.md 里一条不够硬的约束，
那是要修的东西，不是要藏的东西。

## 回报

两层都跑完后，把这些发回来：

1. `run_acceptance.py` 的完整输出（或 `--json` 的文件）
2. 行为验收.md 末尾那张表，填好
3. 第二层的完整对话记录 —— **比任何结论都有价值**

如果你只想发一样东西，发第 3 项。
